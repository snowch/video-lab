### Specific evidence for O4

The proposed `000.jpg` has burned-in source time **0.00 s** and an unsorted queue. `048.jpg` has **4.00 s** and already shows payments first; `072.jpg` has **6.00 s** and the same sorted order. Thus the outline's proposed labels “before the action, the action, the result” are not supported by those three images. Label them as before/result/later result, or select and verify a different action image. A still of the sorted state does not itself show the click or reconstruct the intervening motion. The visible source-time labels particularly require the new output schedule to be explained.

## Static versus interactive decisions

Keep the capture pipeline and encoding/muxing relationship as accessible static diagrams with equivalent labels in text. They explain relationships, so animation adds no necessary evidence. A static filmstrip should show which supplied pictures the learner will encode; the real encode/rerun then demonstrates their presentation timing. Distinguish encoding content from putting encoded streams into a container; adding sound is not evidence that the video had to be re-encoded.

Capture, actual processing, probe, playback and editable retained ranges earn controls because they change or inspect the artefact. Controlled recorded copy/encode examples remain useful evidence if clearly tied to their own fixture. Reject the redesign's absolute “Interactions are justified only where they operate on real bytes”: a labelled source/output clock model can earn interaction by testing a concrete timing claim. It must remain a model, not a claimed faulty export. Likewise an explicitly labelled prerecorded result is real recorded evidence, not fake execution; the misleading action would be implying the current click generated it.

## Initial capstone and outstanding verification

Capture/adopt → separate Build experiment → inspect the selected source → make a meaningful edit → replay/download/check it is a coherent initial capstone. It need not wait for advanced audio, captions, compression or AI modules. Those should remain explicitly planned. The checkpoint should refer to the actual output, retained action/readable result, intentional sound or silence, and source-linked kept ranges in the recipe. Checking playback elsewhere is a learner action, not something a browser probe can certify automatically.

The earlier redesign states that stock WASM lacks ffprobe while the builder reports a new real-browser spike with ffprobe available on the pinned core. This review has not inspected that execution and makes no capability verdict. Replace the assumption with the recorded pinned-version evidence before claiming support. Real encode/mux/probe, source retention, processing failure/cancel/retry, offline readiness, supplied-versus-produced result labels, mobile controls and full-path completion remain built-review and test obligations.

**Decision:** proceed with implementation using the agreed design resolutions. No additional theory module, forced personal screen capture or invented graded fault is needed. This is agreement with the proposed design, not confirmation that the corrections or working path have been delivered.
