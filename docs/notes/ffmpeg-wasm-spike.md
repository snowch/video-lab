# FFmpeg WASM spike — verified capabilities of the pinned core

Copyright © 2026 Christopher Snow.

**Date:** 21 October 2026. **Purpose:** the Phase 1 spike required by `docs/notes/curriculum-redesign.md` §6: verify what the pinned `@ffmpeg/core` actually supports before any UI is authored, and record measured timings and sizes.

## Pinned versions and sizes

| Package | Version | Role |
| --- | --- | --- |
| `@ffmpeg/ffmpeg` | 0.12.15 | Browser-side `FFmpeg` class and worker wrapper |
| `@ffmpeg/core` | 0.12.10 | Single-thread Emscripten core (FFmpeg 5.1.4) |
| `@ffmpeg/util` | 0.12.2 | `toBlobURL` and helpers |

Core size: `ffmpeg-core.wasm` **31 MiB** (32,5xx,xxx bytes), `ffmpeg-core.js` 112 KiB. The core must be vendored same-origin into the production build (see "Delivery" below) and loaded only on explicit learner action. It is excluded from the baseline offline manifest (separate opt-in group).

Core identity (from `-version`): `ffmpeg version 5.1.4`, `libavcodec 59.37.100`, `libavformat 59.27.100`, `libavutil 57.28.100`. Configuration: `--disable-pthreads` (single-thread confirmed), `--enable-gpl --enable-libx264 --enable-libx265 --enable-libvpx --enable-libmp3lame --enable-libtheora --enable-libvorbis --enable-libopus --enable-zlib --enable-libwebp --enable-libfreetype --enable-libfribidi --enable-libass --enable-libzimg`.

## Verified end-to-end operations (all in the pinned core, in a worker)

1. **Video-only MP4 from a picture sequence.** `-framerate 1 -i still-%03d.jpg -c:v libx264 -pix_fmt yuv420p -movflags +faststart film.mp4` with 4 original 960×540 JPEGs → exit 0, 34,473 bytes, probed by native ffprobe: `h264, 960×540, nb_frames=4, duration=4.000000, format mov,mp4,m4a,3gp,3g2,mj2`. **This is the Module 1 core exercise.**
2. **Audio generation + mux.** `sine=frequency=440:sample_rate=8000:duration=3` → real WAV (48,078 bytes); then `-i out.mp4 -i tone.wav -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -b:a 32k -shortest av.mp4` → exit 0, 5,753 bytes, probed: video `h264 3 frames 3.0 s` + audio `aac 8000 Hz mono 3.0 s`. **This is the Module 1 mux exercise.** Encode and mux are independently verified from the generated bytes.
3. **In-WASM ffprobe of the produced file.** `ffprobe -v error -show_streams -show_format -of json big.mp4` printed real JSON (streams with `codec_name: h264`, `width: 960`, `r_frame_rate: 12/1`, `time_base: 1/12288`, …). Output arrives on the log stream and is reassembled into JSON. **This is the Module 1/2 inspection exercise — no separate parser dependency needed.**
4. **Stream-copy cut.** `-ss 0.5 -i big.mp4 -c copy cut.mp4` → exit 0, 0.5 s, but **12 frames** (the whole GOP is copied; timestamps are shifted, not trimmed). First decoded picture is byte-identical to the source picture at 0.5 s. **This is the Module 3 copy-versus-encode evidence.**
5. **Re-encode cut.** `-ss 0.5 -i big.mp4 -c:v libx264 -pix_fmt yuv420p cut2.mp4` → exit 0, 0.5 s, **6 frames** (accurate to the requested time). First decoded picture differs from the source frame (re-encoded). **Same evidence, other method.**
6. **Concat (copy).** concat demuxer with a `list.txt` of two identical inputs → exit 0, 24 frames, 2.0 s. (The `concat:` protocol form failed — exit 1 — so the lesson teaches the concat demuxer with a list file, not the protocol.)
7. **Crop + scale.** `crop=480:270:240:135,scale=960:540` → exit 0, real 960×540 output. **Module 4 exercise.**
8. **volumedetect.** On a real 440 Hz WAV: `mean_volume: -21.1 dB`, `max_volume: -18.1 dB` from the log stream. **Module 5 exercise** — levels are parsed from real filter output.

## Measured timings (sandbox, single-thread core, cold per run)

| Operation | Time | Output |
| --- | --- | --- |
| Encode 3× 2×2 PNG @1 fps | ~45 ms | 1,619 B |
| Encode 4× 960×540 JPEG @1 fps | ~145 ms | 34,473 B |
| Encode 12× 960×540 JPEG @12 fps | ~280–315 ms | 23,383 B |
| Stream-copy cut | ~20 ms | 23,383 B |
| Re-encode cut (0.5 s) | ~140 ms | 20,384 B |
| Crop+scale (12 frames) | <1 s | 13,208 B |

These are small-fixture timings in one sandbox; the UI reports an honest indeterminate "encoding locally" state (the core's progress callback reports `progress`/`time` but no reliable percentage for these tiny jobs), never a fake percentage.

## Known limits (verified, must be taught honestly)

- **No desktop capture.** The WASM core has no capture devices; `getDisplayMedia` is the only browser capture path. The UI never implies WASM recorded a desktop.
- **`drawtext` needs a font file.** With no `fontfile`, it fails ("No font filename provided"). The course therefore ships a small openly-licensed font (or uses a pre-rendered callout image via `overlay`) for callout lessons; this is a Phase 4 decision recorded here so it is not rediscovered.
- **`concat:` protocol failed** in this core; use the concat demuxer with a list file.
- **Odd dimensions fail** in libx264/yuv420p ("width not divisible by 2"); the UI constrains inputs to even dimensions and says why.
- **`-loop 1` on a single image does not repeat** in this build; picture sequences (`%03d`) are the reliable way to build from stills.
- **Exit codes:** `exec`/`ffprobe` return the process exit status; 0 = success. Output presence and probed properties are verified before any success claim.
- **ffprobe exit code was 1** on the successful JSON run above (Emscripten `exit(1)` after flushing stdout in this build); the lesson therefore treats **parseable JSON on the log stream** as the success criterion for ffprobe, not the exit code. Recorded here so it is not mistaken for a failure.

## Delivery decision (Vite + GitHub Pages under `/video-lab/`)

The core is **vendored at build time** into `dist/vendor/ffmpeg/` by `scripts/vendor-ffmpeg.mjs` (copies `ffmpeg-core.js` + `ffmpeg-core.wasm` from the pinned `node_modules/@ffmpeg/core/dist/esm/`, records SHA-256 in `docs/notes/ffmpeg-wasm-spike.json`), so the site is fully same-origin, version-pinned, and works on GitHub Pages with no CDN and no cross-origin isolation. The worker wrapper is a small first-party module worker (`src/encode/worker.ts`) bundled by Vite that loads the vendored core. Nothing downloads the 31 MiB core until the learner presses Run in an encoding lesson.

## Sandbox note

The spike ran the pinned core under Node's `worker_threads` with a small web-worker shim (the `@ffmpeg/ffmpeg` ESM build refuses Node and its UMD build needs browser globals). This proves core capabilities and timings; the real browser path is exercised by the Playwright test `tests/encode.spec.ts` against the production build, which is the authoritative browser evidence.
