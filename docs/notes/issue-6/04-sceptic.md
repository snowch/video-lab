## Retained findings

1. **R1 — empty storage-limited workspace cannot restart (medium), retained and extended.** Independently reproduced the fresh empty main `#/capture` case with `IDBFactory.open` throwing `InvalidStateError`: B prepares, but Restart always reports the unsaved-work failure despite no source, note or edit. Repeated the experiment on the standalone workbench: it too shows Files · 0 and cannot restart. The source independently confirms unconditional `project.persistent` and `unsafeStorage` barriers. Storage capability is not itself unsaved work; restarting does not delete inaccessible persistent data. Keep protection for actual session-only files, dirty drafts, composition, pending writes and active processing, while allowing an otherwise empty workspace to update. Evidence: `empty-storage-results.json`, `empty-workbench-results.json` and `evidence/sceptic-empty-{storage,workbench}-restart.png`.
2. **R2 — legacy-save removal/re-download lifecycle fails (medium), retained; proposed root cause remains unproven.** Independently reproduced the exact retained DOWNLOAD → Resume → practice source → reference note → Remove → Read note → Download sequence on the first round. The panel returned to Not saved for offline use with an enabled button and no useful failure; there was an activated controller but no registration, and the app's baseline/encoder caches had been populated. No page exception occurred. This confirms a recovery failure rather than loss of the note. The author's second-register trace contradicts an explanation that every click was merely discarded before registering. Source review shows unregistering a still-controlling registration during removal and then reusing/registering its same scope; stale asynchronous readiness responses are also not fenced. Retaining the small controlling registration while clearing only scoped offline assets is compatible with the issue's “registrations as appropriate” wording, provided readiness remains based on verified assets and removal does not touch user/sibling stores. Either that lifecycle or a fully fenced unregister/re-register lifecycle must pass this exact case and rapid retry. Evidence: `remove-legacy-results.json`, `remove-legacy.log` and `evidence/sceptic-remove-redownload-race.png`.
3. **R3 — Later does not survive closing every window (medium), retained against the new contract.** In a separate persistent Chromium profile, completely saved A, prepared B, chose Later, closed the entire browser process, then reopened the same profile offline. The running build changed from A to B without Restart. Normal worker activation when old clients close explains the mechanism; it does not satisfy issue 6's explicit new requirement. All four issue bodies say “Activate/reload only on an explicit restart action.” Earlier Video Lab behaviour allowed activation after all tabs closed, but the current user request expressly implements this later issue. Preserve preparation separately from durable authorisation to select the new snapshot; closing/reopening a deferred complete save should retain A and the pending offer, and a later explicit Restart must select B even if its worker has naturally become active. Evidence: `natural-results.json`, `natural.log` and `evidence/sceptic-deferred-after-all-tabs-closed.png`. The immediately captured startup text is not evidence that B lost offline completeness; no such extra finding is claimed.
4. **S4 — legacy download messages now emit incompatible first replies (medium), newly retained.** Tested the actual worker with the old client's one-message MessageChannel behaviour. String `DOWNLOAD` first returned `{progress:true, done:403992, total:9650704}`; string `DOWNLOAD_ENCODER` first returned `{progress:true, done:111804, total:32367068}`. The old client closes its port and resolves that first payload, so `ready` is undefined and it treats a continuing download as failure. Actual later STATUS/ENCODER_STATUS became complete, proving that this is a protocol error rather than a failed asset transfer. Retain the old string commands' single terminal `{ready:...}` reply. Use a new structured request for progress-capable callers; do not require an old client to know that it must ignore progress. Evidence: `legacy-replies.mjs`, `legacy-replies-results.json` and `legacy-replies.log`.

## Rejected or limited claims

No independent basis to claim that a cached release check reports Up to date, that removal deletes user/sibling data, or that ordinary open tabs reload merely because B is prepared. The reader supplied passing real-browser evidence for those other paths; the source's release request explicitly bypasses caches and the fetch handler excludes release metadata. Pending Update ready while disconnected is explained by a separate cannot-check paragraph and does not assert freshness, so the reader's non-finding is upheld.

The removal root-cause hypothesis is deliberately narrower than the demonstrated symptom. An unconditional capability veto is retained only with the reproduced empty state; actual unsaved media and input still require protection. The normal close-all worker lifecycle is not called a general platform defect; it conflicts with this issue's requested deferred-selection contract.

These runs used local real HTTP origins, actual worker/cache operations and two real builds. I did not independently rerun the entire quality gate, Firefox, the reader's true fresh-offline FFmpeg/native-output experiment, quota experiments, physical installations or public deployment. The independent checker must verify the four ranked fixes in the resulting built page, including regression protection for real busy/unsaved work, scoped removal, close/reopen defer and old client replies.
