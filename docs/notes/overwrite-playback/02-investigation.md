# Same-filename overwrite audio investigation

Copyright © 2026 Christopher Snow.

29 October 2026. Read-only product investigation; no repository files changed. Read AGENTS.md, current docs/plan.md and resolution/audio plan. Tested the already-built dist through Vite preview at http://127.0.0.1:4196/video-lab/. Browser: installed Playwright Chromium headless. Real pinned FFmpeg WASM execution through ordinary application controls, not a fake processing adapter. Native ffmpeg/ffprobe: 7.1.5-0+deb13u1.

## Findings

**No naturally occurring silent audio was reproduced in desktop Chromium.** Five same-path PCM WAV generations and four same-path video/AAC generations remained non-silent in both downloaded/stored bytes and the actual browser media pipeline. The application nevertheless has reproducible preview lifecycle defects: it revokes live player URLs, reloads unchanged media whenever workspace state is rehydrated, and reuses player/error state across resources. A delayed error from a replaced resource can remove its valid replacement.

The exact mobile/device failure remains unproven. A nonzero analyser measurement establishes decoded signal inside the browser pipeline; it does not establish physical speaker output, hardware routing or audible listening by a human. `paused === false` alone was never used as evidence of non-silent output.

### Actual generated bytes and media pipeline

Commands:

```
ffmpeg -y -i bunny-short.mp4 -t 4 -vn -ar RATE audio.wav
ffmpeg -y -i bunny-short.mp4 -t 4 -c:v copy -c:a aac -ar RATE movie.mp4
```

Audio rates in order: 16000, 8000, 6000, 8000, 16000 Hz. Video/AAC rates in order: 24000, 16000, 8000, 16000 Hz. Every command completed. After each run, the script read the actual IndexedDB Blob into a native artifact and ran native ffprobe. WAV was PCM signed 16-bit, stereo, exactly four seconds, with the requested rate. MP4 retained H.264 plus AAC at the requested rate (audio four seconds; copied video/container 4.083333 seconds).

For every inline output, the script connected that actual HTMLMediaElement through AudioContext.createMediaElementSource → AnalyserNode → destination, started playback, and sampled time-domain Float32 data over about 1.2 seconds. Maximum sampled RMS across all nine cases: 0.03076–0.03487. Maximum absolute sample: 0.0770–0.0809. Each media clock advanced about 1.2 seconds. No natural media errors or page errors occurred.

Native `ffmpeg -i ARTIFACT -af volumedetect -vn -f null -` decoded all nine with status zero. Mean level was −31.7 or −31.8 dB; maximum level −16.0 dB. Repeated settings were byte identical: both 16000 Hz WAVs share SHA-256 9e25efdadf4fee84bbe411856abd99b3a1f4099ad6f458336bbf348f47408b2d; both 8000 Hz WAVs share a1f90fa24d79657187709bf210a25c95f3b0b392433cd94b59c882f2a752d0b1; both 16000 Hz MP4s share 647be1d1dfc2c4f17049c95ddd8c1446d41ff89fcc5b120bf99919ac897fc56e.

Files: probe.mjs, results.json, native-levels.json and audio-/video- artifacts in this directory.

### Proven unchanged-source playback interruption

1. Open samples page, Replay source, play bunny-short.mp4.
2. Run bare `ffprobe bunny-short.mp4` in a cell.
3. Source video DOM node is retained (id 1), but its object URL changes, currentTime goes 0.306787 → 0, and paused goes false → true.
4. URL audit records `revokeObjectURL(oldURL)` while that same connected, playing video still has both src and currentSrc equal to the old URL, readyState 4 and time 0.362998. Abort/emptied/loadstart follow and the source reloads.

No overwrite or source mutation is involved. The cause is IndexedDB rehydration producing fresh Blob identities; FilePreview's [file.blob,file.name] effect replaces URLs even for unchanged bytes. freshFiles runs at command start and again before committing a new output; refresh on broadcast performs the same reconstruction.

### Retained Files audio after real cross-window overwrite

A second page in the same browser context overwrote audio.wav from 16000 to 8000 Hz while the first page kept its Files dialog audio player open. The first page reused the exact same HTMLAudioElement (id 3), changed its URL and reset time to zero/paused. This player was actually revoked while still referencing its old resource. Pressing Play again succeeded and the existing MediaElementSource/Analyser measured RMS 0.0306565 and 1.211624 seconds of playback. This confirms the retained-player lifecycle path exists, but natural permanent silence did not occur in Chromium.

### Explicit stale-error fault injection

To test the stale event vulnerability deterministically, lifecycle.mjs deliberately schedules `oldElement.dispatchEvent(new Event('error'))` 60 ms after revoking that element's old URL during a subsequent cross-window 6000 Hz overwrite. This is a fault injection, **not a naturally observed browser decode error**.

By dispatch time the exact same connected HTMLAudioElement had a new URL, loadedmetadata and canplay (readyState 4). The unguarded React onError sets shared `failed = true`; the valid replacement audio element disappears and the dialog says “No preview is available for this file. Download it to open it in another app.” No new blob effect runs to reset it. This demonstrates why changing error state in the same component is insufficient when a browser delivers a queued old-resource event later.

Files: lifecycle.mjs, lifecycle-results.json. Audit labels synthetic events INJECTED_OLD_RESOURCE_ERROR and records the corresponding readyState/current URL.

## Source analysis

- FileManager.tsx:10–65: URL, text and error state live across file changes. Cleanup revokes without pausing, removing src, or resetting media resource selection. Browser media errors have no equivalent to the text read's `live` guard. Audio/video DOM nodes are reused for successive resources of the same MIME family.
- Notebook.tsx source preview is keyed by filename, which does not distinguish overwritten bytes. Files dialog preview is not keyed. Current-cell output is hidden while that cell runs (`!running`), so its usual overwrite path remounts FilePreview and does not exercise this retained-node bug. Other cells/shared previews can retain it.
- Cell.tsx:87–124: asynchronous hash effect uses `live` cleanup, so obsolete hashes cannot commit after effect invalidation. However outputMatches retains its previous boolean during a new validation; the render can transiently bind a previously accepted cell to a newly replaced same-path blob before the new hash resolves. No direct permanent-silence mechanism was demonstrated from this alone. A replacement hash mismatch then unmounts its result normally.
- Workspace.tsx:327–365: output transactions copy each Blob into independent backing bytes before writing; IndexedDB writes are transactional. run builds a Blob from the returned output and computes a content hash. No ownership violation found.
- processing/engine.ts: each run creates and ultimately terminates its own worker; there is no persistent same-name core file/cache across runs. Inputs are copied with input.data.slice() before transferable wrapper writes; returned WASM readFile bytes are copied into a new Uint8Array. The saved outputs and repeat hashes support that the bytes survive teardown correctly.

## Recommendation

Prioritise the preview resource lifecycle, with an independently keyed resource component for each actual Blob revision. Give each resource its own URL and error/text state; stop/reset old media before revoking its URL, and prevent detached/obsolete errors from marking the new resource failed. Filename alone is insufficient. A URL should never be handed to a player while that URL is already revoked.

Also avoid unnecessarily reloading unchanged artifacts during workspace refresh. Any retained identity scheme must compare a trustworthy revision/content identity; filename/size/type alone miss real same-size overwrites. This is a separate measured defect from the reported mobile silence and should not be advertised as proof of its exact cause.

Useful regression checks: real WASM same-path WAV and MP4 overwrite with nonzero decoded analyser signal and native output inspection; retained Files preview replacement; deterministic delayed old-node error isolation; URL cleanup verifies no old media retains src/currentSrc before revoke; bare ffprobe preserves an unchanged source preview if identity preservation is included.
